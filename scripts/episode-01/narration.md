## Chapter 01 — 为什么需要局部几何 LOD？

假设我们有这样一块岩壁。

它由数百万个三角形构成。靠近观察时，岩石表面的裂纹和轮廓非常清晰。

但如果把它放进游戏场景，我们真的每一帧都需要画出这些三角形吗？

显然不是。离相机越远，一些几何细节在屏幕上就越难分辨。为此，传统渲染管线常常为一个静态 Mesh 准备多个不同精度的 LOD。

离得近，使用高精度；离得远，切换到更简单的几何。

[动画停顿：同一个 Mesh 在三档 LOD 间切换，观众看见远近的细节取舍。]

这很有效。现在我们把相机移到岩壁的一端。

这块岩壁非常长：离我们近的一端占据大量像素，但远处那一段可能只剩下很小的投影。

如果我们仍然**为整块 Mesh 选择同一个 LOD**，为了保住近处的细节，就可能需要同时保留远处大量没有必要的三角形。

反过来，如果为了远处降低复杂度，直接把整个 Mesh 切到低精度，近处的轮廓就可能损失过多。

这个问题，不是 LOD 本身错了。其他分块或层次 LOD 技术早已能做到局部精度调节。

我们现在真正需要的是：**让几何细节的选择粒度比整个 Mesh 小得多，并且能自动生成这些局部 LOD。**

[动画：同一张网格近处细、远处粗；随后恢复高精度，局部三角形被染成几个 Cluster。]

这就引出了 Nanite 的基本几何单元：Cluster。

但不能只是随便把每一百多个三角形放进一个袋子里。

下一个问题是：**怎样划分，才能让 Cluster 既好管理，又好简化？**

## Chapter 02 — Triangle Clustering

我们现在有一张高密度的三角形网格，希望把它分成许多小 Cluster。

最省事的方法是什么？按三角形在索引缓冲里的顺序，每隔一段就分为一组。

但这显然没有保证：这些三角形在几何上彼此相邻。

[动画：按索引顺序染色时，同一种颜色散落在多个区域；随后撤销。]

一个四处散落的 Cluster，会有很大的空间包围范围。这不利于后续的 Cluster Culling，也往往带来更多分散的边界。

我们需要考虑三角形之间的邻接关系。

可以做一个非常自然的变换：把每个三角形缩成位于其重心的节点，把共享一条边的两个三角形连接起来。

这样，一张三角网格就变成了一张图。

[动画停顿：三角形连续缩成节点，共享边连续转成图边。]

现在，Cluster 的划分就是一个 Graph Partitioning 问题。

我们希望每一组的三角形数量不要超过预算，同时尽可能减少跨越不同组的连接。

为什么要在意被切断的连接？

因为在这张图里，被切断的边代表两组三角形之间的共享边界。边界越多，后续简化可能需要保护的几何约束就越多。

[动画：分区线扫过图；每条被切断的边亮起，计数器增加。]

在经典 Nanite 的公开方案中，一个 Cluster 的目标三角形上限为 128。除了边界数量，还要考虑顶点数量、Cluster 的 Bounds 和 GPU 执行效率等因素。

这里最重要的不是记住 128，而是理解两个核心需求：**大小受限，跨 Cluster 边界尽量少。**

[动画：图节点回到原来的三角形，Partition 颜色留在 Mesh 上。]

至此，我们有了最初的 fine Clusters。

但现在问题来了。

我们是不是只需要给每个 Cluster 再生成一个更低精度版本，然后把它们挂成一棵树就行了？

## Chapter 03 — Cluster Group 与 Simplification

先来做一个实验。

有两个相邻的 Cluster，它们原本沿同一条边连接。

现在，我们分别运行几何简化器。

左边删除了一个边界顶点，右边却把这个顶点保留下来。

[动画：两个独立的 Collapse 产生不同的边界划分。]

注意它们之间发生了什么：两侧不再拥有相同的边界表示。这样可能形成裂缝或者 T-junction。

最直接的办法，是在简化每个 Cluster 时，锁定它所有需要与邻居对齐的边界。

那么，两边就不会因为独立改变这条边界而失配。

但新的问题随之出现。

[动画：内部不断折叠，黄色锁定边越来越显眼，剩余可折叠区域变少。]

Cluster 本来就不大。如果大量边界始终被固定，简化器能调整的几何就会越来越少。

如果我们希望反复简化出很多层 LOD，这个限制会非常明显。

那么，可不可以不把每个 Cluster 都当成独立的简化单位？

我们试着把几个相邻的 Cluster 放在一起，组成一个 **Cluster Group**。

[动画：四块 Cluster 并拢；原本亮起的内部共享边变暗，只保留整个 Group 的金色外边界。]

现在，只需要固定整个 Group 的外边界，就可以把组内所有三角形放到同一个列表中进行简化。

原本跨 Cluster 的共享边不再必须被单独保护。

因此，我们获得了更多简化自由度。

可是，哪些 Cluster 应该放到同一个 Group 呢？

我们又遇到了 Graph Partitioning。

只是这一次，图节点不是 Triangle，而是 Cluster。两个 Cluster 共享的三角形边越多，它们之间的连接权重就越大。

我们希望在大小等约束下，尽量减少跨 Group 的边界总成本——这样需要固定的外边界就更少。

[动画停顿：同一组 Cluster 被划分成两套不同 Group，比较被锁定的外边界长度或边数。]

现在，我们完成了一次 Grouping。接着把整个 Group 的三角形合并，保护外轮廓，然后进行几何简化。

[动画：真实拓扑操作逐次发生，顶点移动、退化三角形移除；边界保持原样。]

但是，简化后的几何可能仍然有很多三角形，不能直接塞进一个 Cluster。

所以，还要对简化后的三角形再次进行 Partition，把它们拆成新的 coarse Clusters。

这一步叫 Repartition，也就是构建流程中的 Split。

[动画：四个 fine Cluster 对应的几何，简化后被重新染色成两个 coarse Cluster。]

我们得到了一个非常有意思的关系：**四个 fine Clusters，共同对应两个 coarse Clusters。**

请记住这组关系。因为接下来，它将决定我们的层级数据结构到底长什么样。

## Chapter 04 — 为什么形成 DAG，而不是 Tree？

我们通常会用 Tree 表示层级细节。

比如，一个父节点对应一片区域的粗模型，子节点对应这片区域更精细的部分。

但这里有一个差别。

刚才简化时，我们把四个 fine Clusters 的三角形混在一起，整体简化，然后再划分成两个 coarse Clusters。这里并不是为每个 fine Cluster 单独生成一个父 Cluster。

新的粗粒度 Cluster 不需要各自一一对应某个旧 Cluster 的局部区域。

[动画：试着给四个 fine 节点各画一条唯一的父边；对照几何覆盖后发现，这种强行分配无法表达整体替换。]

真正可以被替换的，是整个 Group 所代表的那片几何。

原来的四个 fine Clusters，是它的一种表示。

新的两个 coarse Clusters，则是相同外部边界下更简单的另一种表示。

[动画：两份几何并列，但共享边界完全重合；随后切到关系图。]

在依赖关系上，四个 fine 节点会共同关联到两个 coarse 节点。这是一种多对多关系。

所以，在**不改变这套 Grouping / Merge / Split 构建关系**的前提下，我们自然得到的是 **Directed Acyclic Graph**，也就是 DAG，而不是每个节点只有一个父节点的简单 Tree。

这并不是说任何局部 LOD 系统都不可能使用 Tree；而是这里的多对多替代关系，用普通单父节点的 Tree 无法直接表达。

不过，DAG 不是为了让图更复杂。

我们还需要继续重复刚才的构建操作。

把新生成的 coarse Clusters 放回候选集合，再次进行 Grouping。

这时候，一条在上一轮被锁住的 Group 外边界，可能变成新 Group 内部的一条边。

[动画：旧边界从金色变成普通内部边，随后参与一次 Collapse。]

也就是说，这些约束不必在每一层都一直保留下去。

这里真正解决问题的，是**重新分组、合并、简化和重新划分**的过程。DAG 负责表达由这个过程产生的依赖关系。

于是我们就能够一轮又一轮地构建更粗糙的几何。

[动画：多个几何层级持续向上生长，许多 Cluster 节点之间产生交叉依赖。]

到这里，可能会有一个疑问：既然 DAG 中存在大量可选节点，运行时是不是可以任意挑几个来画？

当然不行。

对某次 Group 替换来说，我们可以使用完整的 fine 集合，或者使用与之相容的完整 coarse 集合。

但不能随意抽出一部分 fine，再掺入部分 coarse，否则可能造成几何覆盖不完整或重叠。

我们把满足这些依赖约束、能完整覆盖几何而不随意重复覆盖的一次 LOD 选择，直观地理解为在 DAG 上找到一个合法的 **Cut**。**DAG 上的任意节点集合，并不自动构成合法 Cut。**

至于 GPU 如何高效找到这个 Cut，这是第二期要解决的问题。

现在，我们先停在 Offline Build 阶段。

还有一个问题没有回答：当两份几何都能覆盖同一块区域时，**我们怎么判断其中更简单的一份，究竟损失了多少精度？**

## Chapter 05 — Geometric Error

回到几何简化器。

一张网格里可能有很多候选边可以折叠。究竟先折叠哪一条，顶点应该移动到哪里？

一个经典的答案是 **Quadric Error Metric**，简称 QEM。

我们可以把顶点附近的多个三角形看成若干平面，再估计候选顶点偏离这些平面的代价。

对于一个平面，顶点到这个平面的平方距离可以写成一个二次形式。

把多个平面的贡献累积起来，就能得到一个用来比较候选 Collapse 的误差函数。

[动画：从平面距离线段到若干二次曲面；最后两条候选边亮起不同的 cost。]

这样，简化器可以倾向于选择代价较低的操作，而不是随机删除三角形。

实际的 Nanite 简化还要处理 UV、法线等属性、权重与数值稳定性。我们不在这里展开完整的简化器实现。

这里需要区分一个常见误解：**QEM 的内部折叠代价，并不等同于玩家最后看到的像素误差。**

对于 LOD，我们真正关心的是：低精度几何相比原先的几何，有多大的偏差？

[动画：简化前后的曲面叠在一起，被偏移的表面用透明线段标出。]

而且，我们的几何简化是递归发生的。

从原始几何简化到 LOD 1，会产生一些误差；从 LOD 1 再简化到 LOD 2，又会引入新的误差。

只看最后一步的变化，不足以说明 LOD 2 相对于原始几何的全部偏差。

所以需要把层级中已有的误差考虑进去，并构建保守的误差记录。

[动画：从叶节点开始，误差的表示沿 DAG 向上更新。]

还有一个更重要的要求：当我们沿着 DAG 从 fine 走向 coarse 时，用于 LOD 选择的误差不能反而变小。

这就是单调性。

为什么需要单调？

假设我们有一个固定的误差阈值。

如果同一条依赖路径上误差忽大忽小，那么路径上可能出现多次“满足阈值”和“不满足阈值”的交替。

要找到正确的切换位置，就可能需要检查更多路径信息。

[动画：阈值线穿过一条非单调误差曲线，出现多个交点；随后把它调整为单调曲线，仅有一次过渡。]

如果保证误差从 coarse 到 fine 按要求单调，阈值就能沿每条路径产生明确的过渡。

这为运行时使用局部误差判断、并行决定哪些 Cluster 需要被画出，提供了重要条件。不过，完整的选择条件还涉及 coarse/fine 的依赖关系，我们放到第二期解释。

需要强调的是，Nanite 关心的不只是离线存储的一个误差数字。

最终还要把误差根据 Camera 投影到屏幕上。因此，用于投影误差的 Bounds 也必须与这种单调性相容。

最后来看一个简单的实验。

[动画：相同的几何偏移量固定不变，相机从近处缓慢向后移动。]

同样的几何偏差，在相机很近的时候可能占据很多像素；退到远处，可能连一个像素都不到。

这就是为什么 Runtime 要使用 **Screen-space Error**。

第一期不必把全部公式和 GPU 实现讲完。我们只需要知道：Offline Build 要为运行时准备能够进行这类判断的误差与包围信息。

到这里，我们终于完成了最初那个问题：怎样把一份超高精度 Mesh，整理成支持局部 LOD 的层级数据。

## Chapter 06 — 总结与第二期衔接

让我们再看一遍。

从一张原始 Mesh 开始，我们首先根据三角形的邻接关系做 Graph Partition，得到一组初始 fine Clusters。

然后对这些 Clusters 再次分组。

在保护 Group 外部边界的前提下，合并三角形、简化、重新划分，得到更粗的 Cluster 集合。

多对多的几何替代关系逐渐形成 DAG。

递归构建后，我们还要为这些层级记录误差和用于投影、选择的 Bounds。

[动画：整套构建过程在同一份网格和同一张 DAG 上快速、连贯地回放。]

最终，我们得到的不是简单的几份完整 Mesh LOD，而是一套可以支持局部精度选择的几何层级。

但是，所有这一切，目前都只发生在资产构建阶段。

当游戏真正运行时，GPU 将面对数量庞大的 Cluster。

它怎样判断哪些 Cluster 可见？又怎样根据屏幕空间误差选择合适的 Cut，并最终把这些三角形高效地 Rasterize 到屏幕上？

这就是下一期，我们要讨论的内容。
